# cargo-ai 0.4.5

This release adds usage attribution for packages running from different folders and Cargo AI environments. It is published on crates.io with full Product Qualification and native registry installation verified; see [release status](../docs/testing-and-release-qualification.md#release-status) for source identities and limitations.

## Understand where usage comes from

Newly recorded usage separates the selected environment, logical package, physical package location, agent, consuming workspace and actual runtime. Inspect the effective context without creating a usage database or identity, looking up credentials or contacting a provider:

```bash
cargo ai usage context --json
```

Existing usage queries keep their default schema-v1 output. Opt into schema v2 for named dimensions and filters:

```bash
cargo ai usage summary --schema-version 2 --group-by package,package_location,agent --json
cargo ai usage summary --schema-version 2 --group-by workspace,package --json
```

Other dimensions distinguish environment, runtime version, package revision, agent revision and runtime digest. Missing attribution remains explicitly unknown; upgrading does not reconstruct earlier metadata. Provider attempts count once under the executing agent. Lifecycle counts and durations may overlap between groups and must not be added as independent totals. See [usage queries and coverage](../templates/guidance/usage-ledger.md#local-attribution-and-dimension-queries).

## Keep environments and package copies distinct

An environment is the selected Cargo AI Home, using its existing install identity. One executable can use separate Homes, and several executables can share one Home. An upgrade or a move of the complete Home preserves its identity; copying a whole Home also copies its identity and history. Initialize a fresh Home for an independent environment. There is no physical-machine ID or automatic aggregation across Homes.

A portable UUID in `[project].id` identifies a logical package independently of its name, version, install alias or folder. New project creation/initialization fills a missing ID and preserves an existing valid one. Ordinary execution does not edit project metadata. Copies retain their logical package identity while their locations are grouped separately; moving a package starts a new location group. Legacy packages remain usable with unknown logical identity where no authored or hosted identity is available.

The consuming workspace describes the project that invoked the package, separately from its installed payload location. Updated child agents and tool bridges retain that root caller context while recording their own package and runtime identities. This metadata describes execution; it grants no filesystem permissions. See [Cargo AI Home](../docs/cargo-ai-home.md), [packages](../docs/packages.md) and [projects and tools](../docs/projects-and-tools.md).

## Preserve attribution through optional backup

Updated backup records preserve opaque environment, package, location, agent, workspace and revision references, plus bounded runtime provenance. Local paths, names, agent keys and executable paths stay private. Fresh restores keep the original source environment and an explicit backup namespace; they do not assign historical usage to the destination Home. Restored dimension groups return a `filter_value` for selecting that exact opaque group.

Existing cached or uploaded v1 records remain unchanged, with unavailable attribution still unknown. New enriched uploads wait for server capability support. Older backup clients may refuse enriched selections, and older restore clients receive an upgrade-required failure for mixed snapshots before any page is returned. Upgrade the client or rebuild the generated agent; do not delete history or downgrade records to work around this boundary. Local execution remains independent of backup availability. See [backup compatibility and consent](../docs/usage-backup.md).

## Compatibility and upgrade

This is an additive release on the 0.4.x line with the older backup/restore-client limits described above. Supported definitions and default usage-query output retain their existing contracts. Install or upgrade with `cargo install cargo-ai`, then check `cargo ai version`.

Existing generated binaries do not update automatically. Re-hatch agents to gain attribution or resolve exact-provenance `out_of_sync` status; update/rebuild older tool bridges explicitly to forward caller context. Check `cargo ai guidance status` before explicitly choosing `cargo ai guidance update`, preserving modified guidance and user instructions.

Automatic local usage metadata collection remains enabled by default and can be disabled with `cargo ai usage settings --tracking off`. Backup remains off by default; signing in or enabling future backup does not select historical records. This release adds no billing estimate, automatic cross-environment identity matching or new provider capability. Existing [0.4.4 media limitations](./0.4.4.md) remain applicable.
