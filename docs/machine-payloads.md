# Application payload contracts

Use the [machine interface](machine-interface.md) for output selection, error/exit rules, consent, redaction and compatibility. The application envelope revision is selected by `--output-schema-version 1`; usage's separate `--schema-version 1|2` selects only the payload nested inside it. Existing defaults remain available. Check the installed `capabilities` response before selecting a contract; these interfaces require a build containing them.

The [response schema](schemas/machine-response-v1.json) validates finite frames. The [event schema](schemas/machine-event-v1.json) validates normal `run` NDJSON records. The [catalog schema](schemas/model-catalog-v1.json) validates a model catalog payload. They allow additional fields for compatible additions, reject unknown terminal outcomes, and do not replace command-specific validation below. Frame validity alone does not prove a mutation's postcondition or a complete inventory. Schema examples use illustrative fixture values; they are not live account/provider evidence.

## Shared decoding rules

Every finite frame requires `schema_version`, `payload_schema`, `command`, `build`, `request_id`, `context`, `outcome`, `data`, `warnings`, `error` and `completion`. `payload_schema` is `cargo-ai.<command-with-spaces-replaced-by-dots>.v1`, including hyphens in leaf names, except action discovery/validation which select `.v2` or native role `.v3`. `build` contains version, developer-tools availability, OS and architecture. Context reports explicit/default home selection and the existing shared profile-name keychain scope; use `usage context` for the effective home and persisted environment identity. Request IDs identify an invocation, not an idempotency key or usage run ID.

`completion.complete:true` means a complete terminal response was delivered. Inventory completeness, committed usage coverage, runtime execution and known results have separate fields. `succeeded` requires a null error; every other outcome has a structured error with `code`, safe `message` and `retryable`. Consumers must inspect outcome and required data fields before updating their state. Missing data, null values and unknown enum values do not mean zero, false, removed or successful.

Effect fields are operation-specific. Profile/backup effects use `applied`, `unapplied` and `unknown`; account/package facts also use `not_attempted`, `not_requested`, `unchanged`, `persisted`, `failed` and `not_required`. Preserve each meaning. A failed invocation may already have applied effects. Reconcile authoritative state before retrying; neither a request ID nor a false retryable flag supplies recovery by itself. A `partial:true` failure reports known earlier work, not permission to replay it.

Decode JSON integers losslessly. Existing usage token/count/duration fields remain JSON integers, with token sums checked against unsigned 64-bit overflow. Runtime event sequences are unsigned 64-bit integers. Do not route these through a floating-point-only representation. Usage snapshots and boundaries, and backup failure counts `uploaded_records`/`remote_accepted_records`, are decimal strings. Profile output limits are unsigned 32-bit integers; temperatures are finite nonnegative numbers or null. Durations named `_ms` use milliseconds; profile timeout, session expiry durations and runtime budgets use seconds. UTC timestamps use RFC3339; identifiers, digests, versions, provider/model names and opaque filter/cursor values are strings, not numbers to normalize.

## Profiles and project creation

A profile object always contains `name`, `server`, `model`, `auth_mode`, `is_default`, `token_presence`, `timeout_in_sec`, `temperature`, `max_output_tokens`, `url_present`, `url`, `url_redacted`, `url_origin` and `description`. Thinking-capable builds also return `thinking`: null for inheritance, `{"mode":"provider_default"}` for explicit reset, or `{"mode":"choice","value":"high"}` for an exact opaque choice. Older payloads may omit this additive field. Nullable overrides retain provider-default/absent semantics. `server` and model identifiers remain opaque strings; do not replace unknown providers with a default.

Token presence is `present`, `absent`, `unknown` or `not_inspected`; no token value is returned. A readable inline legacy token can establish presence even when the saved-store lookup fails. List does not inspect credentials. Safe parsed URLs retain their exact configured spelling. A URL with userinfo, query, fragment or invalid syntax returns `url:null` and `url_redacted:true`; a safe HTTP(S) origin may be supplied in `url_origin`. Keep the configured URL when editing unrelated fields; null from redaction is not an instruction to clear it.

| Leaf | Required successful `data` and decisions |
| --- | --- |
| `profile list` | `profiles`, nullable `default_profile`, `ordering:"configuration_order"`, `complete:true`, `next_cursor:null`, `effects`. Missing/invalid configuration is an error, separate from a configured empty list. |
| `profile refresh-context NAME` | `context:{profile_uuid,connection_generation}`, `postconditions_verified:true`, effects for explicit protected local metadata refresh; no provider invocation. See [native role context](#native-role-contract-and-resolution). |
| `profile show NAME` | `profile`, `effects`. Reads the selected profile and token presence without startup migration. |
| `profile add NAME ...` | `profile`, `effects`, `postconditions_verified:true`. Metadata-only add uses the existing first-profile default rule; `effects.managed_home` discloses explicit first-home creation. A collision returns `requires_interaction`; use separate `profile set` calls to change an existing profile. There is no machine replacement-consent flag. |
| `profile set NAME ...` | `profile`, `changed_fields`, nullable `token_change`, `effects`, `postconditions_verified:true`. The existing parser allows one update per invocation. `token_change` is `updated`, `cleared` or null. Effects distinguish metadata, credential persistence and necessary credential preparation. Saved metadata/default and exact requested credential state are checked after the production operation. |
| `profile remove NAME --yes` | `removed:true`, nullable `default_profile`, `effects`, `postconditions_verified:true`. Explicit selected-mode consent is checked before effects. Config removal with failed credential cleanup returns partial work, `removed:true`, and unknown credential effect. Legacy removal retains its prompt. |
| `new PATH --vcs none` | `project_root`, `metadata_path`, `metadata_status`, `gitignore_path`, `gitignore_status`, `vcs`, `effects`, `postconditions_verified:true`. Paths refer to the requested local target; `skipped` means a managed file/VCS operation was not requested. An existing target fails without changing it. Creation failure can leave uncertain ancestor-directory effects even when target cleanup succeeds. |

Profile mutations never call a provider to verify model availability. Use model discovery separately; listing and successful metadata persistence still do not prove inference access.

## Account and authentication leaves

Account and hosted reads may refresh and persist the existing session. Where present, `session_persistence` is `not_required`, `persisted` or `failed`. Failed refresh persistence can make an otherwise confirmed operation partial. Service field projections copy only named scalar facts; omitted optional service facts remain absent, and backend UI/messages/credentials are excluded.

| Leaf | Required successful `data`; optional projected service facts |
| --- | --- |
| `account status` | `account`, `plan`, `session`, `session_persistence`, `readiness:"authenticated"`. Account email must be usable. Optional account `handle`/`status`, plan `code`/`name`, session `refreshed`/`expires_in_seconds` are copied when provided. Status may refresh the session; it is not a passive credential-free check. |
| `account register EMAIL --yes` | `email`, `code_request`, `email_delivery`, `local_email_persistence`. `code_request:"accepted"` means the service accepted the request, not that email arrived; delivery is `not_checked`. An already-authenticated same-email branch reports `already_authenticated:true`, `code_request:"not_needed"` and unchanged local email. Switching a configured account still requires the existing interactive flow. |
| `account confirm --stdin` | `remote_confirmation`, `credential_migration`, `required_local_persistence`, `credential_persistence`, `metadata_persistence`, `reactivated`, `deletion_cancelled`, `session_persistence`. Success requires confirmed remote credentials and required local persistence. Migration contains `changed`, `profile_tokens_migrated`, `account_tokens_migrated`; none contains secret values. Supply a closed nonterminal pipe, maximum 1,024 raw bytes. |
| `account deactivate --yes` | `deactivated:true`, `deletion_requested`, `deletion_completed:false`, `local_state:"preserved"`, `session_persistence`. Explicit deletion requests use existing `--request-deletion --confirm-email EMAIL`; request acceptance is not completed deletion. |
| `auth login openai --profile NAME` | Selected mode returns `requires_interaction` before helper launch, with `effects`, `interaction:{kind,command,verification}` and `format_exception:"interactive_helper_protocol"`. Complete the existing terminal/browser flow, then use legacy `auth status --json`. Short-lived codes/URLs are not ordinary machine diagnostics. |

Never put confirmation codes or API keys in argv. Selected confirmation requires `--stdin` before credential preparation; the legacy positional confirmation syntax is retained for compatibility. Profile token stdin is bounded to 16,384 raw bytes and rejects terminal input, empty/multiline/NUL/invalid UTF-8 values.

## Packages and hosted definitions

Installed package objects require `alias`, `package_name`, `package_version`, `profile`, `content_sha256`, `installed_at`, `source`, `permissions`, `entrypoints`, `capability_source:"installed_manifest"`. Source contains `kind`, nullable local path, hosted source/version IDs and owner handle. Permissions contain package payload/data, project workspace and subprocess policy strings. Each entrypoint has `name`, `path`, `runnable` and `hatchable`; preserve manifest order. This is manifest capability, not a fresh provider/requirements assessment.

List payloads require `items`, `count`, `available_count`, `complete`, `next_cursor:null`, `continuation:"repeat_with_all"`. Installed aliases sort ascending; the existing default limit remains 20. Use `--all` or the existing limit selector rather than treating a truncated page as the entire inventory. Hosted list order is the service response order after existing filters/display limits. Its `available_count` and completeness refer to that returned service dataset; they do not establish a global account snapshot, hidden-access inventory or resumable server pagination.

| Leaf/variant | Required successful `data`; optional service projection |
| --- | --- |
| `packages list` installed | The list payload above, containing installed package objects. No account lookup. |
| `packages list --account [HANDLE]` hosted | List payload plus nullable `owner_handle` and `session_persistence`. Each item requires `project_name`; projected `project`, `project_version`, `owner_handle`, hosted IDs, public/archive flags and `updated_at` may be absent. |
| `packages inspect ALIAS` installed | `package`, `data_root`, `requirements_assessment:"not_performed"`. Existing legacy inspection retains its richer human requirements report. |
| `packages inspect NAME --account [HANDLE] [--version SEMVER]` or supported account-bound immutable selectors | `package_manifest`, `session_persistence`; validated snapshot identity includes `project`, `project_version`, owner/source/version IDs, digest and package size when supplied. Existing `--json` inspection remains a separate legacy domain contract. |
| `packages install SOURCE --as ALIAS` local; hosted install selectors | `action`, `installed_effect`, `package`, `readback:"verified"`. An unchanged install reports `installed_effect:"unchanged"`; changed installs report applied. Installed-manifest readback establishes the reported identity. Failures retain retrieve/prepare/materialize stage and unknown/not-attempted installed/staging effects. Hosted permission acceptance uses the existing `--accept-permissions`, with no implied approval from output selection. |
| `packages pull --source-id ID --version-id ID --output-dir DIR` | `output_path`, `retrieved:true`, `local_effect:"applied"`, `session_persistence`; projected package name/version, owner, immutable IDs, SHA-256 and byte size. Retrieval/extraction failure does not establish installation; uncertain local effects require inspection. |
| `packages visibility --name NAME --public|--private` | Confirmed `project`, `public`, `remote_effect:"applied"`, `session_persistence`; optional archive flag. Mismatched service identity/visibility is an unknown outcome. Refresh the hosted inventory before retrying. |
| `package [PROFILE] --output-dir DIR` | Developer-tools builds only: `output_path`, nullable project name/version, `profile`, `manifest`, assembled/archive/estimated-request byte sizes, `archive_sha256`, `local_effect:"applied"`. Assembly copies source; it does not itself establish a build or publication. |
| `packages publish` | `request_id`, `package_sha256`, `remote_effect:"applied"`, `receipt_persistence:"persisted"`, `session_persistence`; projected package/version and immutable hosted IDs. The request ID/digest comes from the exact prepared publication. Remote acceptance with failed local receipt is partial; inspect retained receipts and authoritative hosted state before any retry. |
| `agents list --all [--owner-handle HANDLE]` | List payload plus `session_persistence`. Each item requires `agent_name`; projected `agent`, namespace `definition_path`, owner, visibility/archive flags and update time are optional. Keep owner and namespace selectors on later reads/mutations. |
| `agents pull --name NAME --definition-path NAMESPACE --stdout` | `definition` object, `retrieved:true`, `file_persistence:"not_requested"`, `session_persistence`; projected agent/namespace/owner identity. Explicit output-file variants report persisted output path. Legacy `--stdout` returns the raw definition; selected mode carries it under `data.definition`. |
| `agents push --name NAME --definition-path NAMESPACE --json-file FILE` | Confirmed `agent`, optional namespace/owner/visibility/archive scalar facts, `session_persistence`. `--json-file` remains the definition input. No definition is reconstructed from console prose. |
| `agents visibility --name NAME --definition-path NAMESPACE --public|--private` | Confirmed `agent` and `public`, optional namespace/owner/archive facts, `session_persistence`. Unknown or mismatched confirmation is not success. |

Paths and manifests describe the existing approved local operation; output selection does not change overwrite rules, permission policy, project boundaries or execution authority. Package installation can invoke Cargo and publisher code; package retrieval alone is not an execution claim.

## Declared client actions

Catalog/request 2 remain supported, with explicit native role catalog/request 3. Revision 1 and unknown action-interface versions are rejected before execution. Outer envelopes/events, execution policy and static-resource transport retain revision 1. The project-root [catalog schema](schemas/action-catalog-v2.json) describes strict `cargo-ai-actions.json` declarations; its `discovery` definition separately describes the typed list response, including compiled capabilities/limits. [Request](schemas/action-request-v2.json), [binding](schemas/action-binding-v1.json), [execution policy](schemas/action-execution-policy-v1.json) and [resource](schemas/action-resource-v1.json) specifications cover their separate identities. Machine envelope/event revision stays 1. These JSON Schemas document the language-neutral shape; runtime validation also checks byte/depth/count limits, path confinement, references, selected distributions and destination compatibility. Authored business schemas never load references, regular expressions or network schemas.

| Leaf/variant | Required successful `data` and decisions |
| --- | --- |
| `actions list --project PATH` or `--package ALIAS` | `schema_version:2` or `3`, `supported_catalog_versions:[2,3]`, `supported_request_versions:[2,3]`, `binding`, `actions`, `interfaces`, `resources`, `artifact_scopes`, `capabilities:["execution_policy.v1","business_inputs.v1","structured_results.v1","artifact_access.v1"]`, `limits`. Actions retain declared IDs, labels/descriptions when present, target, input schema, mapping descriptors, constants and required capabilities; `result` is the target definition's exact selected-result declaration or null. Interfaces select action/resource subsets and optional presentation entrypoint. Catalog 3 adds `role_registry` and capability `native_roles.v1`. Discovery reads verified declarations/bytes without execution. |
| `actions validate` | `schema_version:2` or native `3`, `valid:true`, `execution_authorized:false`, `interface`, `action`, `binding`, `mappings:{runtime_vars:[names],inputs:[names]}`. No submitted business values or attachment contents are echoed. Successful validation is advisory; dispatch revalidates. |
| `actions resource` | `schema_version:1`, `binding`, `interface`, resource `id`, `mime_type`, `size_bytes`, `content_sha256`, `encoding:"base64"`, `data`. Decoded bytes must match size/digest; the response grants neither execution nor private-store path access. |
| `run --action ID --interface ID ... --action-request-stdin` | Existing run result/event payload plus additive `client_action:{interface,action,binding}` after resolution. Private content retains existing opt-in and result availability semantics. |

A legacy action request requires `schema_version:2`, `interface`, `action`, `inputs`, `expected_binding`, `execution_policy`; optional `attachment_grants` is a host-controlled map and `artifact_access:{version:1,scopes:[IDs]}` is separate native artifact permission. Select exactly one explicit project/package target, with CLI IDs matching the request. Business values obey the selected action's declared schema and mappings. Structured, null and nullable values need `encoding:"json"` into a string runtime variable or text input; scalar destinations retain existing types. File/image values use `{grant_id,content_sha256}` and a matching host grant `{path,content_sha256}`; a page cannot supply authorization by naming an arbitrary path. URL mappings retain HTTP(S) input rules. Constants cannot collide with mappings.

Bindings contain opaque `root_sha256`, `catalog_sha256`, `content_sha256`, and optional installed `package:{alias,version,content_sha256}`. Copy discovery's entire binding; catalog-wide target/resource changes invalidate it even when the selected action is unchanged. The request's interface/action remain separate selectors. Resource stdin is `{schema_version:1,interface,resource,expected_binding}`. The host binds the declared resource inventory/MIME and verified bytes to its authorized document generation.

Execution policy uses `version:1`, `allowed:[{profile,request_kind,model,thinking}]` and `limits:{max_runtime_secs,max_output_tokens,max_agent_depth}`. `profile` is an explicit name or null; request kinds are `text`, `image`, `audio`, `transcription`. Model is `{kind:"named",value:ID}`, `{kind:"provider_default"}` or `{kind:"fixed_service"}`. Thinking is `{mode:"provider_default"}`, `{mode:"choice",value:CHOICE}`, `{mode:"on"}` or `{mode:"off"}`. Every record grants one exact combination. Missing/default/fixed choices do not mean unrestricted selection. Fallback to provider default requires a matching grant as well. The client constructs this policy from explicit authorization and permitted discovered settings; it is distinct from project/business data. An empty allowed list denies provider selections, including existing root selection for action-only execution. Ordinary runs without an action policy retain their behavior.

Legacy discovery/validation payload identities are `cargo-ai.actions.list.v2` and `cargo-ai.actions.validate.v2`; native role catalog/request 3 select their `.v3` counterparts. Discovery `limits` also exposes `business_key_bytes`, `result_bytes`, `producer_payload_bytes` and an `artifact` object with read types, file/request/response bounds, nomination/chunk/JSON limits, `native_confinement` and `authorization:"trusted_host_grant"`. The machine `run.structured_results` descriptor declares the definition revision, source, supported business types/nullable union, private-content and descendant boundaries, and artifact access. Discovery `limits` uses numeric fields `catalog_bytes`, `actions`, `interfaces`, `resources`, `request_bytes`, `business_depth`, `array_items`, `object_members`, `resource_bytes`, `inventory_bytes`, `definition_bytes`, `attachment_bytes` and `string_bytes`; the machine action descriptors expose the same values. Limits: catalog 256 KiB, 256 actions, 64 interfaces/resources, request 64 KiB, business-value/schema depth 8, 64 object members and 1,024 array items. Declared root definitions are at most 1 MiB; each resource is at most 4 MiB decoded and total target/resource inventory at most 16 MiB. Attachment verification retains the 10 MiB file limit. Policy is at most 32 KiB with 128 combinations; runtime is 1–86,400 seconds, output tokens are positive unsigned 32-bit and agent depth is 0–64. Runtime/input/media limits still apply separately. String/metadata byte bounds and unsupported-keyword checks are runtime-enforced rather than inferred from frame validity.

Errors distinguish `action.invalid_catalog`, `action.invalid_request`, `action.unknown_interface`, `action.unknown_action`, `action.stale_binding`, `action.resource_denied`, `action.unsupported_capability`, `action.invalid_inputs`, `action.unsupported_contract` and execution-policy errors (`action.execution_policy_invalid`, `action.execution_selection_denied`, `action.execution_limit_denied`, `action.execution_policy_unsupported`). A declared-action error is not consent to broaden grants or replay uncertain effects. Opaque generated-child failures may remain a supervised child failure without an inner typed policy reason.

`client_action_resolved` and later event metadata carry the same correlation as terminal `data.client_action`; early `operation_started` has none. Decode the existing stream incrementally, retain operation IDs and require terminal evidence. A client handle, usage run ID and CLI request ID are different identities. No second lifecycle, schedule storage or exactly-once execution contract is introduced.

### Shared business schema and selected results

The [business schema](schemas/business-schema-v1.json) applies to action inputs and the [selected tool result](schemas/structured-result-v1.json). Supported types are object, array, string, integer, number, boolean, null and exactly `[T,"null"]`. Objects are closed and require explicit `required`; arrays are typed. Enum, descriptions and supported length/numeric bounds are allowed; authored references/patterns/arbitrary unions/unknown keywords fail. Nonempty business keys have at most 128 UTF-8 bytes and no control characters; `__proto__`, `prototype`, `constructor` fail at every depth. Schema-declared settings/model/config/profile/policy-like keys inside `inputs` are data, never native authority. Duplicate JSON keys fail.

Business data is at most 65,536 serialized UTF-8 bytes, depth 8, 64 members/object, 1,024 items/array and 65,536 bytes/string. A complete action request is still at most 65,536 bytes including native policy/binding/grants, so hosts must calculate and recheck the smaller effective editable budget. Return a selected record or bounded edit projection rather than assuming an entire result fits a save request. Hosts must preserve supported integer values exactly or report unavailable; string IDs/versions avoid JavaScript rounding.

Definition revision `2026-10-03.r1` adds `result:{source:"tool",schema:BUSINESS_SCHEMA,artifact_scopes:[IDs]}` with exactly one concrete root tool step marked `produces_result:true`. After a successful tool exit and valid existing tool protocol, its result string decodes as `{data:VALUE,artifacts:[NOMINATION]}`; data is required, nominations default to empty. The wrapper is bounded to 131,072 bytes and 64 unique nominations. Bare protocol null is missing; wrapped business null is valid only when the schema permits it. A model-backed definition still computes its action input; only the selected tool supplies the root result, with no provider/child/capture/stdout fallback. Skipped or unreached producers yield `not_produced`.

`data.result` retains availability and `content_included`. `--include-result-content` gates `content`, `artifact_references` and `artifact_read_grants` together. Native artifact permission is an additional requirement for issuance. Without private opt-in none of these private fields is present. Read grants and locators are host-only even with consent: hosts must construct page-safe terminals rather than forwarding CLI data unchanged. Progress, usage and safe diagnostics do not contain this private result.

Result errors are `runtime.result_missing`, `runtime.result_invalid`, `runtime.result_schema` and `runtime.result_limit`. An already validated result can survive a later failure/cancellation or failed export, but the terminal outcome retains that failure and earlier data does not certify final state. Missing/invalid output does not prove a mutation was unapplied. Never retry automatically.

### Authorized artifact reads

Catalog scopes are `{id,path,mime_types}`; interfaces and producer declarations select subsets and native `artifact_access` grants a reviewed subset. Source projects require explicit runtime-data opt-in; installed aliases use existing owned data and held leases. Context identity includes installation incarnation, so returning an alias to identical version/content does not revive an old grant. Mutable media do not become static presentation resources. Scope declarations alone never authorize reads.

Nominations are `{id,scope,path,mime_type}` with unique ASCII IDs of at most 128 bytes and portable scope-relative paths of at most 1,024 bytes. Successful issuance creates a [private descriptor](schemas/action-artifact-descriptor-v1.json) and a separate [host-only read grant](schemas/action-artifact-grant-v1.json). References are domain-separated grant identities, not signatures/bearer tokens/historical-issuance proof. Native consent/document identity and exact host registry lookup authorize use; the CLI independently verifies confinement and current context/bytes. A trusted same-user caller can synthesize an internally consistent in-scope grant.

`actions artifact --project PATH --interface ID --request-stdin --output-format json` (or `--package ALIAS`) accepts the [artifact request](schemas/action-artifact-request-v1.json): `{schema_version:1,interface,expected_binding,reference,read_grant}`. No top-level file path or URL is accepted. Its successful `cargo-ai.actions.artifact.v1` [payload](schemas/action-artifact-v1.json) is `{schema_version:1,binding,interface,reference,mime_type,size_bytes,content_sha256,encoding:"base64",data}`. This explicit private read needs no result-content flag. It performs no agent/tool/provider/network execution or state initialization.

Advertised read types are UTF-8 text/plain, application/json, image/png and audio/wav; one file/read is at most 4,194,304 decoded bytes. Artifact request maximum is 65,536 bytes and reference maximum 128 bytes. JSON parsing is bounded to depth 32 and 65,536 nodes; PNG/WAV processing to 4,096 chunks. Base64 plus metadata remains inside the 8 MiB finite-response cap. Format checks are not a playability/decoder-safety/rendering guarantee. PDF, final video, larger narration and unadvertised types are unavailable. There is no streaming, range retry, arbitrary-file API or implied renderer. Discovery advertises native confinement separately; unavailable confinement must deny rather than fall back.

The reader rejects links/reparse points, multiple hard links, nonregular files, traversal and byte/context changes using held handles. Typed errors include `artifact.export_failed`, `artifact.invalid_request`, `artifact.access_denied`, `artifact.stale_binding`, `artifact.stale_context`, `artifact.content_changed`, `artifact.not_found`, `artifact.unsupported_type`, `artifact.unsafe_file`, `artifact.size_limit`. Errors disclose no private locator/content. Hosts keep grants and bounded byte caches private and revoke access on document/binding/context/permission changes; previously displayed bytes cannot be retracted.

One failed nomination invalidates that entire export set; valid business data remains with failed/partial outcome and no newly issued references/grants. Use separate actions for optional previews so useful records and independently authorized available previews survive a missing/stale/denied attachment. Required artifact groups may stay atomic. Neither failure nor stale media permits mutation replay or another ungranted transport.

## Usage and backup

Selected usage success always requires `usage`, `effects`, `postconditions_verified`. The `usage` value is the unchanged released domain payload, including its own schema revision. Reads report unapplied local/remote effects; tracking changes report verified saved settings. `postconditions_verified:false` on a read does not mean the read failed; it indicates no mutation postcondition was requested.

| Leaf | Required nested facts and pagination |
| --- | --- |
| `usage context --json` | `usage.schema_version:1`, `effective_home`, `environment`, `runtime`, `attribution_schema_version`, `query_schema_versions`, `grouping_dimensions`. Inspection does not initialize missing identity/home or look up credentials. |
| `usage summary --json` v1/v2 | `schema_version`, decimal `snapshot`, `coverage`, `summary`, `groups`. V1 groups use ordered array keys and are unpaged. V2 adds `group_by`, object keys with typed attribution/filter values, snapshot-bound `next_cursor` and bounded group pages. Groups sort by canonical serialized key; totals are snapshot totals, not a sum to repeat for every page. |
| `usage runs --json` v1/v2 | `schema_version`, `snapshot`, `coverage`, `runs`, nullable `next_cursor`. Runs sort by first committed matching sequence; entries include root ID, child agent IDs, summary and status. Preserve unknown statuses such as `interrupted_or_running`; they are not a heartbeat or proof of current execution. |
| `usage show RUN_ID --json` v1/v2 | `schema_version`, `snapshot`, `coverage`, ordered `events`, nullable `next_cursor`. Events sort by committed sequence, not wall-clock time. A valid empty event page can mean no captured facts; it does not prove run completion. |
| `usage settings --json [--tracking on|off]` | `schema_version:1`, `coverage`, `settings:{tracking,backup_enabled,backup_account_binding,backup_generation}`, `effective_tracking`. Tracking and backup remain independent; an environment override can make effective tracking differ from the saved setting. |

Runs/show default to 100 records, with `--limit` in 1–1,000. V2 summary group limit is also bounded to 1–1,000. Keep the selected home, command, run identity, exact opaque filters/grouping and payload revision with the cursor. V2 validates that binding; a fresh uncursored call starts a new snapshot. V1 cursor behavior remains its legacy behavior rather than gaining v2 guarantees. Capture coverage is `committed_events_only`; process loss and unknown usage never become zero. V2 attribution retains known/none/unavailable states and restored account namespaces. See the [usage attribution contract](../templates/guidance/usage-ledger.md#local-attribution-and-dimension-queries).

Selected backup success requires `backup`, `local`, `effects`, `postconditions_verified:true`. `backup` is the existing leaf payload, and `local` is readback of queue counts, snapshot, enabled state, account binding and generation. Status counts are integers; boundaries such as `snapshot`, `through` and `future_records_after` are decimal strings. Local account queue ordering is binding/generation ascending and capped at 100 groups, with `account_queues_truncated` disclosed. A generation is a positive signed-64-bit-compatible integer; account bindings are opaque UUID strings.

| Leaf | Required `data.backup` facts |
| --- | --- |
| `usage backup status --json` | Local pending/acknowledged/unscanned counts, account queues/truncation, snapshot, enabled state, binding and generation. `--remote` explicitly changes the payload to `{local,remote}` and permits an account request; default status is offline. |
| `usage backup enable --json` | `enabled:true`, binding, generation, future-record boundary, `historical_records_selected:0`. Remote acceptance precedes local queue/settings changes. Failure effects keep remote acceptance and queue/settings uncertainty separately. |
| `usage backup disable --json` | `enabled:false`, `history_deleted:false`, `queued_selections_preserved:true`. Queue pause may already be applied when settings persistence fails; history is retained. |
| `usage backup sync --json` | `enabled`, `uploaded_records`; when enabled, batch count, binding/generation and local queue status. Explicit sync is at most ten 100-record batches in 30 seconds and stops on first failure. ## Runtime and model discovery

`run` accepts existing target/input/profile/runtime flags plus selected JSON or NDJSON output. `run --json` still supplies definition input; `--include-result-content` separately opts into private validated root result content on stdout. Successful terminal `data` requires `execution:{completed:true}`, `result`, `artifacts`, `child_instrumentation`, and `effects`. Failed execution retains available runtime-known facts. Result availability is `available` with explicit content or `content_included:false`, or `not_produced`; it is separate from action completion. Artifact metadata reports successful generated image/audio writes as `{kind:"image"|"audio",state:"produced",path,content_included:false}`. Empty artifacts do not establish that an arbitrary program wrote no files. Opaque child execution supplies exit/diagnostic counts, no invented result or telemetry; `child_instrumentation:"unavailable"` discloses this.

Normal NDJSON event types are `operation_started`, `provider_completed`, `action_started`, `action_completed`, `child_started`, `child_completed`, `subprocess_completed`, and `operation_completed`. Action/step indexes are zero-based. Diagnostic byte counts describe bounded captured channels, not a transcript. All frames in the current implementation share one operation/root/invocation ID; usage root/agent run IDs have a separate identity contract. Verify equal IDs, contiguous zero-based sequence and a single terminal envelope with matching request ID. Parallel actions can interleave while event sequence remains global emission order. Incremental decoders must handle split UTF-8/lines and reject an incomplete final record. Cancellation/process cleanup and output delivery need their own evidence; a missing terminal frame or unconfirmed cleanup never means completion. Forced termination and delivery/bootstrap failures may leave output outside the normal stream contract.

`models list` returns the catalog described by the [catalog schema](schemas/model-catalog-v1.json). Complete catalogs are `data`; a bounded page/time-budget result returns outcome `partial`, error `discovery.partial`, and the catalog under `data.catalog` with `partial:true`. A complete empty catalog is successful. The catalog requires provider/auth, safe connection origin and nullable saved-profile name, `fetched_at`, `source:"live"`, `cache:null`, `complete`, nullable continuation, pages fetched, models and `invocation_access:"unverified"`. Models require exact selectable `id`, nullable display `name`, provider metadata, `metadata_source:"provider"` and unverified invocation access. Gemini metadata retains `resource_name` while selectable ID removes `models/`.

Provider/page order is preserved, with first-seen ID deduplication. Completeness means the known provider pagination finished for this connection, not that inference was authorized or that paged reads form an immutable server snapshot. Discovery auto-pages at most 20 requests, one MiB per response and 30 seconds total; `--page-limit` can reduce the page bound. Partial continuation is `{available:false,reason:"page_budget_exhausted"|"time_budget_exhausted"}` with no resumable cursor. A timeout before any valid page remains a failure; a later budget timeout retains only completed validated pages. Discovery supports the listed native OpenAI, Anthropic, Gemini, Mistral, xAI and Ollama connection shapes; unsupported layouts require manual entry. Saved API-key discovery requires explicit file storage; draft keys use bounded stdin. No inference, credential persistence, profile/home initialization or cache write follows from listing.

For `auth:"openai_account"`, saved and explicit draft connections use one bounded direct Codex catalog response. Exact `slug` values become `id`; only explicit picker-visible records are returned. `complete:true` describes that validated visible selection; hidden models may still be entered manually. Unknown capabilities and invocation access remain unverified. The existing Codex session must have known selected account context, supported commercial routing and a fresh token. No account identifier, token, raw JWT or credential-derived identity is included in the payload. A session/configuration change during the operation fails safely; a new invocation follows the current Codex session. Separate Cargo AI homes do not isolate that shared session. See [account discovery boundaries](machine-interface.md#models).

New account catalogs include `compatibility` with `kind:"codex_backend"` and a nonempty `client_version` string matching the adapter's request query (currently `"0.159.2"`). This optional additive field carries no account identity. It is not the installed CLI version, an automatic upgrade instruction or proof of model availability. Consumers must accept older payloads without it and tolerate future compatible fields; API-key/no-auth catalogs omit it.

## Runtime thinking

The [thinking schema](schemas/model-thinking-v1.json) defines shared setting, support, outcome, scope, record, collection and runtime-capability types. A provider request record is `{scope,outcome}`. Scope is `{kind:"invocation"}` or `{kind:"action_step",action_index,action,step_index}`, with a zero-based definition action index and a zero-based index among that action's platform-matching steps. Outcome requires nullable tagged `requested`, `source`, tagged `support`, nullable `applied`, tagged `effective`, nullable `fallback` and nullable explanatory `reason`. Source records `profile`, `invocation`, `step`, `step_profile` or `provider_default`. A supported named choice has its exact value in `applied` and `effective`; a supported Boolean setting has canonical `"on"`/`"off"` in `applied` and the corresponding tagged mode in `effective`. Wire effort encodings do not become named levels; fallback has `applied:null` and `effective:{mode:"provider_default"}`. No concrete provider-default level is invented. These fields describe adapter request selection; an outcome recorded before inference does not prove that the request completed or the provider accepted it.

Unavailable choice, unsupported control and unknown support produce distinct fallback values `unavailable_choice`, `unsupported_control` and `unknown_support`, and warning codes `thinking.choice_unavailable`, `thinking.control_unsupported` and `thinking.support_unknown`. Warnings carry scope, requested setting, categorical reason and effective default. Outcome `reason` supplies the detailed explanation. A default selection can have unknown support because discovery was unnecessary; it produces no fallback warning.

Child forwarding records require `scope`, `kind:"child_forwarding"`, tagged `requested`, `disposition:"forwarded"|"not_forwarded"`, `declaration_source:"embedded_artifact"|"unavailable"` and `effective:"child_unverified"`. Even a supported forwarded flag is not child inference telemetry. Missing/invalid declaration omits the flag and adds `thinking.child_capability_unavailable`; it preserves the child's existing configuration and execution/error behavior.

Optional terminal `data.thinking` requires `records`, `omitted_records` and `coverage:"complete_observed_scopes"|"bounded_partial"`. Collection retains at most 256 records, 16 KiB per record and 512 KiB total; omitted facts add `thinking.outcomes_truncated`. Complete observed coverage concerns only reached, observed scopes, not skipped actions or opaque child internals. These facts and warnings remain available after progress omission and on terminal failure; they do not change the operation's outcome, exit code or consent/effect semantics. NDJSON adds `thinking_resolved` carrying one record, with the existing event IDs, sequence and delivery bounds.

## Native role contract and resolution

[Catalog 3](schemas/action-catalog-v3.json) adds required `role_registry` to catalog 2's portable declarations. The [role registry](schemas/role-contract-v1.json) has `version:1`, `roles`, `call_sites`, `contexts`, and optional `tool_content`. Role requirements declare an exact operation (`text_generation`, `image_generation`, `speech_generation`, `transcription`), input modalities, structured output and finite allowed setting values. Role IDs and call-site IDs are stable package identifiers. Each role may optionally carry up to eight nonpersonal `recommendations`, each with `provider`, `model`, `operation`, optional `settings` (default `{}`), `provenance` and `rationale`. Provider/model text is nonblank and at most 256 UTF-8 bytes; provenance has 1–8 nonblank strings of at most 2,048 bytes each, and rationale is nonblank and at most 2,048 bytes. All these text fields reject control characters. Operation uses the same four operation tokens; settings use the existing exact tagged thinking, voice, format and temperature syntax. Unknown fields, including profile/account/context selections, are rejected. Absent or empty recommendations are valid; native catalogs omit an empty array. Suggestions may differ from the role requirements: they are advisory presentation data, never bindings, capability evidence, verified access or policy/consent, and do not constrain resolution. `different_model_from` names other roles whose selected provider/model pair must differ. A missing comparison binding yields unknown `missing_comparison_binding` and prevents readiness, even when that role is outside the selected context. A known equal pair remains incompatible. Comparison bindings do not add call sites or policy grants; recommendations cannot satisfy the comparison. Each call site carries `{definition,site}`, its native kind, requirements, and exactly one role or fixed selection for actual inference. A structural `child`/`tool_child` may omit both only when its verified target has no root inference; resolution then uses `selection:null`, compatible `structural_native_child`, without inventing a model grant. Root sites describe real root inference only; selected child root inference must match the target root and appear in each reachable context. Direct children declare exact JSON `target` and optionally exact generated executable `artifact`; native tool children additionally declare a closed business `input_schema`. `tool_content` inventories the exact portable files for each declared tool. Runtime checks the complete graph, unique locators and actual definition/tool/source inventory; valid JSON alone is insufficient.

Contexts select exact `{action,interface,mode}`, call sites, resources, data scopes and limits. Resolution checks the shared role binding against every active use's constraints, including unioned input modalities and structured-output needs. Contexts remain separate for controls and timers even when roles are shared. A role mapping is never a permission, resource grant or execution result.

[Request 3](schemas/action-request-v3.json) retains request 2's binding, inputs, policy and grants, and adds `role_execution:{binding_revision,mode,resolution_id?}`. A binding revision has `{version:1,revision,bindings:[{role,profile,profile_uuid,connection_generation,provider,model,settings}]}`; it belongs to host-private storage. Settings are exact tagged `thinking`, `voice`, `format` and optional bounded `temperature`; media settings do not inherit text reasoning. Omitted thinking selects provider default. Native role settings replace the selected profile's model/thinking/temperature defaults. The host changes its revision identifier when choices change. `actions resolve` permits `resolution_id` omitted; validation/execution require the exact returned digest, with no fabricated placeholder.

`cargo-ai.actions.resolve.v1` data follows [resolution 1](schemas/role-contract-v1.json#/$defs/resolution): `identity`, `binding_revision`, `binding_identity`, `context`, `scope`, `calls`, `required_selections`, `ready`, `execution_authorized:false`, `invocation_access:"unverified"`, and `version:1`. Each call includes exact site/selection/settings, categorical compatibility, reason and native evidence. Evidence carries exact UUID/generation/provider/model/operation/input/settings dimensions, provenance, evidence revision and expiry; `operation_evidence` adds reviewed endpoint/transport/output/settings constraints and freshness. Statuses are `compatible`, `incompatible`, `unknown`, `stale`, `unavailable`. Mapped calls require compatible evidence for readiness. Structural children have no inference selection. Disclosed fixed calls may remain `unknown` yet ready for explicit legacy selection policy; this does not relabel their operation compatibility or invocation access. Native fixed profiles still require fresh protected connection context. Catalog listing or configurable reasoning alone cannot establish compatible output operations or invocation entitlement.

Canonical identities serialize typed values with sorted object keys, preserve array order and hash the compact JSON with SHA-256. The six native context digests bind project root, selected native home, complete package `ActionBinding` (including installation identity), actual runtime contract, validated protected connection references, and exact policy/attachment grants/artifact permission/business inputs. Raw paths and credential comparison material are not returned. The environment digest includes the selected home identity and existing/absent state. A structural scope with no role bindings or fixed connections identifies an absent home through bounded absolute path normalization and existing-ancestor canonicalization without creating it; later home creation invalidates that resolution. Actual selected profiles require existing protected state. Hashes identify this candidate; they are neither signatures nor authority. The resolver validates execution-policy syntax and never imports host assertions as capability evidence. Dispatch re-resolves and compares the reviewed identity; changes require new review. Execution additionally rejects policy selections outside this scope's `required_selections`, limits above its ceilings and grants outside the actual selected action/interface context. There is no implicit union of imported permissions or attachment grants.

`cargo-ai.profile.refresh-context.v1` retains its existing successful [data shape](schemas/profile-context-v1.json). It explicitly enrolls or repairs protected native context; unchanged effective connections preserve the same opaque UUID/generation. Routine callers validate the expected reference using the continuity contract below. Passive resolution never logs in, repairs state or writes metadata. Neither clock age nor unrelated configuration edits invalidate approval. A changed or recreated connection cannot inherit old authority. Failures retain safe role attribution without credential or endpoint dumps.

[Session frames](schemas/native-role-session-v1.json) have `protocol:"cargo_ai_role_session"`, `version:1`; strict inputs are `start` with an executable request, or `revoke`/`cancel` with `binding_revision`. A wrong revision returns `control_rejected` with `role.revision_mismatch`. Matching controls acknowledge `revoked`/`canceled`, invocation/revision, duplicate flag, closure reason and outstanding admission boundaries. `effects:"admitted_work_may_settle"` discloses the revocation limit; cancellation's `owned_child_cleanup` is `requested` or `unconfirmed`.

Acknowledgement lines have no machine-event sequence, bypass progress omission and must be decoded separately. Their bounded writer has one pending queue slot and a two-second deadline from just before nonblocking enqueue through writer completion receipt. Full queue, write error or timeout closes/requests closure with `control_output_lost`, cancels and requests owned-child cleanup; missing acknowledgement delivery remains uncertain. The terminal snapshot preserves the first closure reason; later output loss or control-limit cancellation may retain an earlier `revoked` reason. Revocation closes admission before the acknowledgement attempt; failed delivery additionally cancels the invocation. At most 256 successfully read post-start frames are handled across the invocation, including mismatches and malformed frames; malformed input terminates immediately. After the 256th handler/acknowledgement attempt, `control_limit` requests closure/cancellation without a 257th read. The 1,048,576-byte limit includes LF per frame, so accepted controls have a 256 MiB aggregate wire maximum after the separately bounded start; there is no 4 MiB aggregate session budget.

Terminal `data.native_role_execution` contains invocation/revision, `closed` reason or null, outstanding permit boundaries, bounded outcomes (`completed`, `failed`, `not_dispatched`, `completion_unknown`), `omitted_outcomes` and `complete` meaning no outstanding permits. Permit completeness does not establish business success; read the terminal envelope's outcome too. At most 256 outstanding permits and 256 outcome records are retained independently; omitted outcomes are explicit. The host cannot convert a lost child/terminal result into success or automatically replay it.

Each boundary carries `invocation_id`, `binding_revision`, `call_site`, `agent`, `kind`, nullable `parent_permit_id` and nullable `target_agent`. The session identity remains shared across all descendants and controls revocation. Join `parent_permit_id` to the owning native-child or tool outcome's `permit_id`; root boundaries have a null parent. Each admitted launch has a distinct permit, including repeated or overlapping launches of the same definition. Nested provider and tool work retains that launch lineage, validated by the native pipe that owns it. `agent` identifies the executing definition; a child attempt's `target_agent` identifies its declared destination, even when denial prevents launch. Resolve `call_site` against the reviewed registry for its role. A pre-admission denial has an empty `permit_id`, retains its actual parent/site/target and reports `not_dispatched`; it does not create an admitted child. Correlation grants no authority. If bounded outcome omission removes a referenced parent, show incomplete attribution rather than guessing from array order or claiming success.

Safe role failures include unsupported/invalid declarations or bindings, unknown context, context unavailable, stale resolution, package changed, undeclared call site, selection/setting/limit denial, child rebuild required, revoked/canceled and child/control completion unknown. Preserve private choices and drafts on failure. Validate the saved profile reference with `profile validate-context`; use `--renew` when verification evidence needs renewal. Unavailable or uncertain continuity pauses affected work without discarding approval. Meaningful changes require affected review and explicit enrollment through `profile refresh-context`; do not use enrollment to silently accept a new identity. Rediscover/rebuild when source/capability identity changed, and reconcile admitted effects before a retry. Neither unsupported media nor missing native-tool capability permits a shell/tool/provider fallback.

### Connection continuity and remembered approval

Negotiate `connection_continuity.version:1` in runtime capabilities and the profile validation command before relying on continuity. Remembered package approval has no time-based expiration. It is separate from credential validity, capability evidence and native permission for each invocation.

```sh
cargo ai profile validate-context example \
  --profile-uuid APPROVED_UUID \
  --connection-generation APPROVED_GENERATION \
  --output-format json
```

Add `--renew` to refresh public verification evidence and protected local metadata after an unavailable-evidence response. This operation does not renew provider tokens or change the approved connection identity. The expected reference must come from the saved reviewed setup. Never synthesize one or replace it merely because a command returned another generation.

The [validation payload](schemas/profile-context-validation-v1.json) reports a typed status, `execution_ready`, `review_required`, safe reason, context and effects:

| Status | Host response |
|---|---|
| `unchanged`, `renewed` | Retain saved approval and choices. Resolve the actual action request and exact policy again before execution; validation grants no permissions. |
| `changed` | Retain choices and obtain affected review of the changed connection or setup. Do not silently reuse old authority. |
| `unavailable`, `unsupported` | Pause affected execution and explain the connection problem. Retain approval and choices; repair or await evidence, then validate again. Uncertainty is not proof that consent was revoked. |
| `revoked` | Reject the old reference. Ordinary validation or renewal cannot restore revoked authority. |

Checks and successful verification renewal of a shared unchanged profile do not invalidate other packages using that profile. Effective provider, endpoint, authentication, account/principal, model/settings, package requirements/source and authorized-scope changes remain relevant. Each action retains its own exact policy and resolution; consolidated setup never combines grants. Native authorization and revision-specific active-session revocation remain mandatory. A revoke acknowledgement does not undo already admitted effects.

Account continuity supports the native OpenAI account transport when the actual access token has a valid trusted signature and the supported issuer/audience, account/principal, client and scope fields. The selected account must match the authenticated token. Codex retains credential ownership: Cargo AI does not refresh its tokens or write its credential file. An ID token alone, a matching profile name, or decoded unsigned claims do not establish continuity. Missing, unsupported, expired or unverifiable credentials pause execution. A protected public-key cache has bounded freshness; refreshing it for an unchanged identity requires no new approval. Cache freshness is not a consent timer or proof of provider invocation access.

Unchanged API keys are compared through the selected protected credential store. Replacing an opaque key without trustworthy account-continuity evidence requires affected review. No-auth connections compare effective connection settings without claiming authenticated remote identity. Unsupported account transports/layouts remain explicitly unsupported rather than silently falling back.

Older protected records can retain their reference during explicit migration only when their protected comparison still matches the actual current credential/configuration and native code establishes the new continuity evidence. If an older record cannot establish that link, retain choices and require explicit enrollment/affected review. Passive resolution does not migrate records.
